# 0.7.19 — le canal de mise à jour compare les octets, pas les commits

## Le défaut

`check_update` décidait « installe ceci » en comparant des **commits**. Mais le commit
enregistré à l'installation est la pointe du dernier `fetch` — régulièrement un commit
qui n'a touché que `scripts/` ou `docs/`.

Mesuré sur 0.7.18, au moment où j'ai publié v0.7.18 puis corrigé la suite de tests :

```
installe     : 0.7.18 | commit 045eac35 | tag v0.7.18
head main    : 320de7d0
dernier commit touchant extension/ : 37e958d5
update_available : True    from 045eac35  to 37e958d5
```

Et l'arbre `extension/` :

```
320de7d  c1090d37b44b81eb   (changelog)
d11f3d2  c1090d37b44b81eb   (harnais de peinture)
045eac3  c1090d37b44b81eb   (suite de tests autonome)
fccabaa  c1090d37b44b81eb   (suite sans secret du poste)
37e958d  c1090d37b44b81eb   (la vraie correction produit)
```

**Cinq commits, un seul hash d'arbre livré.** Quatre d'entre eux ne changent aucun
octet de l'extension installée. Le popup proposait donc de réinstaller un octet
identique — et aucune installation ne pouvait vider la pastille, puisque le `fetch`
suivant enregistrait à nouveau un commit non livré.

## Le correctif

Le filtre par sous-arbre (`shipped_commit`) était déjà juste ; il compare par **sha**.
La vraie question est : *les octets déposés ont-ils changé depuis le dernier commit
livré ?*

Deux nouvelles fonctions, une requête de plus, jamais plus d'un coup :

- **`shipped_tree_sha(repo)`** — `/git/trees/main?recursive=1` liste chaque blob sous
  `extension/` avec son propre sha ; on hache les paires `(chemin, blob)`.
- **`local_tree_sha(ext_dir)`** — le même haclage sur les fichiers déposés.

`check_update` compare les deux, et **repli sur la comparaison de commits** si la
consultation échoue : un update inutile vaut mieux qu'un update manqué.

### Trois pièges, tous rencontrés

1. **Le schéma de hachage.** L'API renvoie des sha de **blob git**, donc le local doit
   faire `sha1(b"blob <len>\0" + octets)`. Un `sha256` nu compare deux alphabets
   différents — il signalait une différence sur les **14 fichiers livrés**, tous
   identiques octet pour octet.
2. **La clé du chemin.** Le distant liste `extension/popup.js`, le local calcule un
   chemin relatif au dossier. Deux alphabets encore, donc aucun arbre ne correspond
   jamais et l'update est offert indéfiniment.
3. **`.build-info.json`.** Écrit par l'installeur, non suivi, différent sur chaque
   machine. L'inclure rend chaque arbre unique — la comparaison perd tout sens. Un test
   modifie **uniquement** ce fichier et exige que le hash ne bouge pas.

## Preuve rouge

`scripts/proof_red_update_channel.py` — **5 sabotages, 5 rouges nommés, 0 invalide**.

Les cinq sabotages cassent un lien chacun : la comparaison par commits, le message
explicatif, le schéma de hachage, le préfixe de chemin, l'exclusion du
`.build-info.json`.

### Trois pièges de harnais, tous consignés dans le skill

- **Sabotage qui supprime l'argument de formatage.** Remplacer `"...%s..."` par
  `"rien a faire"` lève `TypeError: not all arguments converted` — une défaillance de
  harnais déguisée en rouge. Il faut réécrire le **message** et garder
  l'interpolation, pour que le rouge vienne de l'assertion et pas d'un crash en la
  construisant.
- **`expect` doit venir du message réellement affiché.** `unittest` tronque une paire
  d'hex à la largeur de la fenêtre : `AssertionError: 'a' != 'b'` ne nomme aucun
  fichier. Le message d'assertion est devenu auto-porteur
  (`build-info.json change : le hash du tree a bougé...`).
- **Sauvegarder les callables dans `setUp`, pas dans le helper.** Les stubs ajoutés dans
  `_stub` sont restés installés pour les deux tests qui n'appellent pas `_stub` : ils
  lisaient une constante résiduelle et mouraient sur
  `AttributeError: no attribute '_real_local'` — la faute pointant sur le produit.

Et un effet de contrat, traité explicitement : les tests qui affirment « un update est
offert » doivent maintenant déclarer que le **contenu diffère**, sinon ils passent pour
la mauvaise raison sous le défaut « arbres identiques ».

## Résumé

- `update_available` passe de `True` à `False` sur l'état réellement mesuré, avec la
  note : `main moved to 320de7d0, but the deployed tree is byte-identical`.
- Un update qui change le produit reste offert (`shipped_tree: differs`).
