# v0.7.12 - a client that never spoke could never be released

## What happened

The relay is a `ThreadingHTTPServer`. Every accepted connection got a thread, and
a thread that waits for a request line that never arrives waits forever.
`Handler` declared no class-level `timeout`, so `StreamRequestHandler.setup()`
left the socket blocking. The `settimeout(10)` inside `do_GET` looked like a
guard but is not one:

```
client connects -> setup()            socket blocking, no deadline
               -> handle_one_request -> readline() BLOCKS   <-- the read that hangs
               -> do_GET() -> settimeout(10)               <-- far too late
```

The deadline was applied *after* the read that a silent client holds open. So the
exact request a client never finishes is the one that gets no deadline at all.

Measured with a probe that opens 25 connections and transmits zero bytes:

```
before fix:  25/25 still open at 12s, 25/25 at 35s, /health answering 200
after fix:    0/25 open at 12s
```

Nothing looked broken. The relay kept answering every request it did receive,
which is why this never surfaced as a user-visible failure: it is thread and
memory exhaustion that only appears under someone else's traffic. `daemon_threads
= True` with no cap is what made it unbounded - I considered a thread ceiling and
rejected it: it would reject `/health` under load, converting exhaustion into an
outage, which is strictly worse than the defect it fixes.

## The fix

```python
class Handler(BaseHTTPRequestHandler):
    timeout = 15
```

One class attribute, applied by `setup()` before anything is parsed.

## The half that mattered as much

A deadline has two ways to be wrong. Too short and it kills legitimate work; too
long and it does not fix anything. 15s is above the relay's worst-case CDP work -
navigate + 1.5s settle, then up to four injection rounds - so a total-duration cap
would have broken session import while every unit test stayed green.

But `settimeout` bounds **one socket operation**, not the request's wall-clock
time, and that is exactly the property worth pinning:

```
handler sleeps 2x the deadline, then answers -> complete response delivered
```

`tests/test_socket_timeout.py` asserts both halves against the real `Handler`.

## The test that lied to me

The first version of that test subclassed the handler with `timeout = 2` to keep
the suite fast. It passed. Then the proof-red run sabotaged
`Handler.timeout` to 600 in `relay/server.py` and **all five tests stayed green**
- because the test replaced the very value it claimed to be testing.

Rewritten to serve the real `Handler` on an ephemeral port; the fast path is now a
wait budget scaled to the real deadline. Proof-red afterwards fails with
`AssertionError: une connexion muette est restee ouverte apres l'echeance` - the
failure names the defect rather than tripping over a missing attribute.

The sabotage run legitimately needs ~600s (the test must wait out the entire
600s deadline before declaring a socket stuck), which exceeded the 400s
subprocess budget and produced a `TimeoutExpired` - a harness failure, not a
result. The `finally` restored `server.py`, verified by grep: `timeout = 15` back,
and the 8 uncommitted diff lines intact. Never `git checkout` for this.

## Verified

- 226 tests green locally.
- Proof-red: sabotaging the class deadline to 600s turns the silent-socket test
  red for the right reason, with no `NameError`/`AttributeError` noise.
- A live gate check opens a real silent socket against the RUNNING relay and
  reports the measured release time, then confirms `/health` still answers 200 -
  so the fix is verified on the installed code, not just in the repo.
- `/health` under a simultaneous 60-request burst: 60/60 answered, import
  refused in 0.40s (that refusal being the intended origin check, not a timeout).
