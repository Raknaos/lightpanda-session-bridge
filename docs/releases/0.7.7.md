# v0.7.7 - the undo point could be destroyed before it existed

## What was happening

`_backup()` opened with `shutil.rmtree(backup_root, ignore_errors=True)` and only
then rebuilt the directory. Anything that failed during the copy - ENOSPC, EPERM,
or a file lock, which is the *normal* case on Windows when Chrome holds `popup.js`
open - left the install with **no undo point at all**, before the live tree had
been touched by anything. The red proof is direct:

```
AssertionError: False is not true : meta.json generation 1 perdu
```

The backup is now built in `extension-backup.new` and swapped in at the end, so
the previous generation is only discarded once the new one is complete and
readable. A `finally` removes both the staging directory and the retired one: a
half-written `.new` would be mirrored from by the next backup, and
`read_backup_meta()` would report the version of an install that never completed.

## The lock, and why it had to be an RLock

`apply_update`, `rollback_update` and `check_update` took no lock at all. The relay
is a `ThreadingHTTPServer` and three different callers reach this module
concurrently: the popup (`/v1/update/apply`, `/v1/update/rollback`), an agent
holding the token, and `python relay/server.py --apply-update`. One thread's
`rmtree` could delete the directory another was mirroring from.

All three now serialize on `_UPDATE_LOCK`. It is an **RLock**, not a `Lock`,
because `apply_update` calls `check_update`. The first version used a plain
`Lock` and the test suite hung for seven minutes before the timeout - a
self-deadlock, which is the honest way to learn that the lock is wrong. The
reentrancy is per-thread, which is what is wanted here: a nested
`check_update` must not block, a second *thread* still must.

## The undo point could not describe itself

Two smaller bugs that only showed up when the backup was finally inspectable.

`_mirror` skips `.build-info.json` on purpose - it belongs to the tree being
replaced, not to the source - so the backup never carried it, and a rollback
restored a tree whose provenance was blank. It is now copied explicitly.

And `meta.json` was filled from `installed_info()` **re-read after the mirror**,
so it described the install that was arriving rather than the one the backup can
restore. The info is now snapshotted before mirroring.

The second one was found by reading the real `meta.json` on disk, not by reading
the code. Production showed two incompatible sources of truth:

```
installed_info()      -> {'version': '0.7.6', 'tag': 'v0.7.6', 'source': 'release'}
read_backup_meta()    -> {'version': None,  'tag': None,         'source': None}
```

After the fix the live report agrees with the deployed tree:

```
{'version': '0.7.6', 'commit': '1128f1a9', 'tag': 'v0.7.6', 'source': 'release'}
```

## Verified

Four sabotages, attributed one by one - and two of them taught something about
the harness:

- `_backup` destructive -> 1 failure, the one named above
- `.build-info.json` not copied -> 1 failure, named assertion
- `installed_info` re-read after the mirror -> `AssertionError: '9.9.9' != '0.7.5'`
- plain `Lock` instead of `RLock` -> the run never finishes (that IS the defect)

Deleting the `installed_info` line outright produced four `ERROR: NameError`s,
which reads like a successful sabotage and is nothing of the kind; the real
sabotage of the same finding moves the line rather than deleting it.

A full apply/rollback cycle was then run against the live install: the backup
recorded `0.7.6` with commit and tag, the rollback restored it, and the restored
tree reports `source: rollback` with the previous version in `previous`.

213 tests green, gate 28/28.
