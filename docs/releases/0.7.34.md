# 0.7.34 - a killed process does not restore what it sabotaged

## The defect

`finally` is not a restore when the process is **killed**. Three proof runs hit
their timeout this session with a live edit still on disk, and nothing caught
them:

| left behind | what it meant |
|---|---|
| `pyproject.toml` at `0.7.99` | a version nobody shipped |
| `popup.js`, translation block replaced | the popup losing a language |
| `relay/diagnostics.py`, `scrub()` -> a literal | **the report printing credentials** |

The last is the one that matters. `scrub()` is the whole reason the diagnostic
report is safe to paste into a public issue; a literal `"[redacted]"` satisfies a
leak assertion that only looks for the marker, and destroys the report's only
explanation of why an operation failed.

Two of the seventeen harnesses had **no `try` at all** around their write/restore
pair:

```python
POPUP.write_text(text.replace(old, new, 1), encoding="utf-8", newline="")
code, out = run_test()          # <- the only call that can hang or raise
POPUP.write_bytes(original)     # <- never reached if it does
```

The other fifteen already had it. `run_test()` is the call that hangs, so an
inline restore after it is precisely the wrong order.

## The fence

Per-harness restoration is a promise; the gate needs a fence. It now
fingerprints every file a proof-red harness edits, before and after the family
runs, and refuses any difference:

```
extension/popup.js, relay/server.py, relay/updater.py, relay/diagnostics.py
```

The check is **independent of the restorations it fences**, so a harness that
restores wrongly fails loudly rather than quietly poisoning the next run - which
is what makes the next harness snapshot a sabotage as its own `original`.

Proven both directions: a harness that restores leaves `drifted = []`; one that
does not leaves `['relay/diagnostics.py']`.

## What my own check got wrong

Its first real run fired on a genuine leftover and reported the **wrong reason**:
the harness verdict, with the drift buried beneath it. A leftover sabotage is a
live defect in the tree; a harness verdict is a statement about the proof. The
tree state outranks it, and one message must not cover two states.

A second measurement of mine was wrong in the same session: I took the
"before" fingerprint *after* applying the sabotage, so the check measured a
damaged baseline and reported drift where there was none. Both directions only
became visible once the reference was captured first.
