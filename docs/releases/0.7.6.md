# v0.7.6 - the restore scripts stacked, and "Tout retirer" was a half-wipe

## What was happening

Every import registered a `Page.addScriptToEvaluateOnNewDocument` whose source
embeds the whole localStorage snapshot, so the snapshot survives future
navigations. Nothing ever called `Page.removeScriptToEvaluateOnNewDocument`.
Measured on the relay's own code:

```
import 0 : 1 registered, 0 removed
import 1 : 1 registered, 0 removed   (2 live)
import 2 : 1 registered, 0 removed   (3 live)
```

So the target accumulated one document-start script per import for the lifetime
of the CDP connection, each rewriting the full snapshot on every page load.

The visible symptom was worse than the leak. `clear_sessions` deletes cookies by
name, one by one - it did delete them. But the restore script stayed registered,
so the next navigation re-applied the entire localStorage. "Tout retirer" left
half the session behind, and a half-wipe looks exactly like a flaky sync: the
user clicks again, it works, then something reappears.

## The fix

- The relay keeps the identifier of the live restore script and retires the
  previous one on each registration. Measured after the fix: import 0 registers
  one and retires none (nothing to retire), imports 1 and 2 each retire one -
  exactly one live script at any time.
- `clear_sessions` retires the script before returning, and clears the stored
  identifier so a later import does not try to retire a script that is gone.
- `_STORAGE_RESTORE_ID` needed an explicit `global`. The first version assigned
  it without one, which wrote a local: the probe still showed 0 removals and the
  suite was green. Worth stating plainly, because the failure mode of a missing
  `global` is silence, and silence is what this file was written to detect.

## Also fixed: the backup's own metadata

`_backup()` writes `meta.json` into the backup directory; `rollback_update()`
mirrors that directory into the live extension. `_mirror` exempted only
`.build-info.json`, so a rollback deposited a stray config file into the shipped
tree - and the next update's prune pass then deleted it as "not in the source
tree". Both bookkeeping files now come from a single `MIRROR_KEEP` tuple, and the
filename is no longer spelled out at its two use sites (rename one and the
exemption silently stops matching, which is exactly the kind of drift that made
this possible).

## Verified

Three sabotages, attributed one by one:

```
no script retirement      -> 4 failures (stack, per-import, clear, global)
clear does not retire     -> 1 failure  (the half-wipe)
meta.json not exempted    -> 2 failures (constant, prune)
```

The prune test is behavioural - it mirrors a real tree into a destination holding
`meta.json` and asserts the file survives while a stale shipped file does not.

Verified live afterwards: `/v1/sessions/clear` returns `cleared: 1`, the list goes
empty, `session.json` is erased, and the diagnostic agrees (`synced_origins: 0`).

203 tests green, gate 28/28.
