# v0.7.2 - the archive guard is proven, not assumed

## What prompted it

A delegated audit reported a missing traversal guard. It was wrong - but reading
the guard to refute the claim showed the tests were weaker than the code.

`tests/test_updater.py` proved two shapes:

```python
archive.writestr("../../evil.txt", "x")   # posix traversal
archive.writestr("/abs/evil.txt", "x")    # posix absolute
```

`_safe_members` does considerably more:

```python
name = name.replace("\\", "/")
if not name or name.startswith("/") or re.match(r"^[A-Za-z]:", name):
    raise RuntimeError("archive refused: absolute path")
parts = [p for p in name.split("/") if p not in ("", ".")]
if any(p == ".." for p in parts):
    raise RuntimeError("archive refused: path traversal")
```

The backslash normalisation plus the drive-letter regex cover the Windows-native
shapes: `C:\evil.txt`, `C:evil.txt`, `//server/share/evil.txt`,
`..\evil.txt`. None of that was asserted anywhere.

## Why it matters

Nothing is broken today. The risk is the next edit: someone tidying
`_safe_members` into the obvious one-liner, 56 updater tests staying green, and
the hole reopening on the single platform this project ships on. A guard that is
read and believed is not a guard - it needs a test that goes red when it goes.

## Verified

- 5 new tests, all red under the sabotage: making validation per-member instead
  of up-front had every Windows shape extracted silently instead of refused.
- Also pinned: a refused archive leaves no partial tree, and a valid archive
  still lands where expected - a guard that refuses everything is not a fix.
- 166 tests green, acceptance gate 28/28. No product code changed.
