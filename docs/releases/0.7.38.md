# 0.7.38 — un fichier livré que rien ne lisait

## Le défaut

`extension/background.js` était le **seul** appelant du relais sans délai. Le popup
route chaque `fetch` par `relayFetch` (45 s) ; le service worker faisait :

```js
const res = await fetch(`${RELAY}/v1/update/check`, { cache: "no-store" });
```

Pas d'`AbortController`, pas de délai. Un relais qui accepte la connexion puis se
tait laissait le service worker en attente jusqu'à ce que Chrome le tue — le badge
de mise à jour gelait **sans erreur visible**.

## Pourquoi la gate ne l'a pas vu

Le check qui affirmed « toute appel du popup porte un délai » ne lisait qu'un seul
fichier. Le comptage est instructif :

| fichier | ouvert par le gate |
|---|---|
| `extension/popup.js` | 3 fois |
| `extension/background.js` | **0 fois** |

Un fichier du produit **livré et installé** avec le même manifest n'était lu par
aucun check. Même famille que les releases précédentes : une propriété vérifiée
pour un composant, jamais pour les autres.

## Le correctif produit

`background.js` route désormais par son propre `relayFetch`, borné à **10 s** — le
worker est court-vivant, il n'a pas besoin des 45 s du popup, il a besoin d'une
borne. Un `AbortError` devient un `RelayTimeoutError` nommé, distinct d'un relais
hors ligne, parce que ces deux états ne se ressemblent pas pour l'utilisateur.

## Le check

`every_shipped_relay_call_is_bounded` ne liste aucun fichier : il parcourt tout
`.js` sous `extension/`. Un cinquième fichier client ajouté l'an prochain est
couvert par construction, pas en spitlant pour remember d'étendre un tuple.

La règle, par fichier : un `fetch(` n'est légitime **que** dans une fonction qui
effectue elle-même le `fetch` borné. Un helper est reconnu **structurellement** —
le contrôleur qu'il crée, le délai qui aborte *ce* contrôleur, le signal passé à
`fetch` *depuis ce* contrôleur, et un `fetch` retourné. Aucune correspondance par
nom.

## Trois faux верts que ce check a d'abord produits

| version | erreur | sabotage qu'elle a laissé passer |
|---|---|---|
| 1 | prenait le **dernier** nom contenant « fetch » | `fetchSessions` (L1111) chosen sur le vrai `relayFetch` (L986) → **rouge sur le fichier sain** |
| 2 | « dans une fonction dont le nom contient fetch » | `refreshUpdateBadge` — le nom *contient* « fetch » sans rien borner → un `fetch` nu passe |
| 3 | `any(owner[0] <= pos <= owner[1] for h in helpers)` | la clause ne mentionne pas `h` : `any()` répondait « y a-t-il *un* helper ? » pour **tout** `fetch` du fichier |

Le troisième est le plus instructif : c'est la famille « une variable itérée jamais
utilisée », invisible à la lecture, et qui ne se révèle pas sur un arbre sain.

Et une quatrième, mesurée : `RELAY_TIMEOUT_MS = 0` passait. Nommer un délai ne
l'honore pas — `0` fait partir l'abort immédiatement, c'est un appel sans attente.

## Preuve d'exécution

Contre un serveur TCP qui accepte la connexion puis ne répond **jamais** :

```
RESULT REJECTED name=RelayTimeoutError msg="relay deadline exceeded"
ELAPSED 10007ms
```

Le délai **tire**, mesuré en millisecondes réelles, pas déduit d'une chaîne
présente dans le fichier.

## Discrimination mesurée

| cas | attendu | obtenu |
|---|---|---|
| produit sain | vert | `ok — 2 shipped client file(s) bounded: background.js (10000ms via relayFetch), popup.js (45000ms via relayFetch)` |
| `fetch` nu hors helper | rouge | `L41 in refreshUpdateBadge (does not carry a deadline)` |
| helper sans `AbortController` | rouge | `L23 in relayFetch (does not carry a deadline)` |
| `RELAY_TIMEOUT_MS = 0` | rouge | `RELAY_TIMEOUT_MS is 0 - a deadline of 0 is no deadline` |
| helper contourné | rouge | `L41 in refreshUpdateBadge (does not carry a deadline)` |
| abort débranché | rouge | `L24 in relayFetch (does not carry a deadline)` |
| signal détaché du contrôleur | rouge | `L24 in relayFetch (does not carry a deadline)` |
| 4ᵉ fichier client nu | rouge | `extension/alarm.js: L2 in pingRelay (does not carry a deadline)` |
| même fichier conforme | vert | `3 shipped client file(s) bounded: alarm.js (5000ms via relayFetch), …` |

## Leçon

Un check qui énumère ses fichiers n'a pas d'invariant : il en a une liste. Le jour
où un fichier est ajouté à la liste n'est pas le jour où on s'en souvient.
