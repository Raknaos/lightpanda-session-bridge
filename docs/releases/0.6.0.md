# v0.6.0 - the report you could have sent me an hour ago

Six of these releases came from screenshots. Every one of them ended the same
way: a number in a popup, no artifact, and a diagnosis that took a guess, a
reading of the relay's stdout by hand, and a lucky reproduction. The product had
no way to tell us what it was doing.

## Copy diagnostic

The footer now carries a button that puts a sanitized report on the clipboard:
deployed version and commit, host and interpreter, which files are present
(fingerprinted, not read), live relay state (CDP attached? transport type? how
many origins synced? how many localStorage keys expected versus applied?), and
the last ten install audit lines. `GET /v1/diagnostics` returns the same report.

**The guarantee: no cookie value, no token, no localStorage value, no browsing
URL.** Counts and names are metadata and do appear. This is enforced twice -
`tests/test_diagnostics.py` plants four realistic credentials and searches the
rendered output, and the acceptance gate plants four more.

The scrubber went through three revisions, each caught by those tests:

1. Matching `"cookie"` and `"storage"` as substring key names deleted exactly the
   fields the report exists for (`storage_expected`, `last_sync_cookies`).
   A count is metadata.
2. Blanking entropy over our *own* structured report ate the product name, the
   timestamp and the file fingerprints. The scrub now applies only to foreign
   data (the install log, written elsewhere).
3. A fingerprint like `900 B sha256:ae35d3da97e6` tripped the base64 rule. Those
   values are minted here and are now exempted first - they are the report's
   proof that the deployed extension is the repo's.

## The archive could not attest to itself

Rebuilding the release zip from one unchanged tree produced a different
sha256 every time. Two independent causes:

- `ZipFile.write` stamps the current time and the build OS into every entry.
- deflate is **not** reproducible across build machines. Measured here: the
  project `.venv` ships zlib 1.3.1, the system python ships `1.3.1.zlib-ng`.
  Same 148 KB tree, 148120 vs 148524 bytes, two digests.

Entries are now STORED with a fixed epoch, a fixed creator and no host metadata:
one tree, one sha256, on every machine. Cost is the honest one - about 150 KB
uncompressed instead of deflated - and what it buys is that the published
sidecar means "these bytes are the committed tree" instead of "these bytes are
whatever this machine's zlib produced".

`scripts/build_release_zip.py` also died with a bare `FileNotFoundError` when
`LOCALAPPDATA/Temp` did not exist - a fresh Windows profile, CI, or any
non-Windows machine.

## Also

- `relay/patch_snippet.txt` removed: a scratch file tracked by git since v0.5.5.
- Three new acceptance checks (diagnostic sanitized, endpoint served, archive
  reproducible) - and they are registered in the LOCAL/LIVE lists, which is the
  part that matters: a check defined but not listed never runs, and a check that
  cannot fail is decoration. Both new sabotages were verified red.
