# 0.7.41 — le gate emptied sa propre liste et a dit « tout va bien »

## Le défaut, un cran au-dessus de 0.7.40

0.7.40 a etabli par la mesure que **trois checks** pouvaient mesurer le vide. Celui d'ici
est le même défaut appliqué au gate lui-même, et c'est le pire endroit possible
où il pouvait se loger.

`the_gate_cannot_contain_a_check_that_cannot_be_seen` est le check qui garantit
qu'aucun check ne peut être invisible au verdict. Il compare des listes :

- `registered = LOCAL + LIVE`
- `ghosts` = noms enregistrés sans fonction
- `helpers` non appelés

Toutes ses invariants sont des **tests d'emptiness**. Une liste vide les satisfait
tous. Vider `LOCAL` et `LIVE` donne :

```
LIVE = []
avant : ok   0 checks: every registered name resolves and is decorated
```

**Vert.** Le gate n'exécute aucun check et sa propre garde le compliments. Seize
checks — la moitié qui mesure le **produit en service** : relais, authentification,
`updates.xml` en direct, Lightpanda, proxy CDP, aller-retour de session, audit,
extension installée, popup traduit — ne se sont pas exécutés, et le verdict a
dit `READY: every check passed.` comme si de rien n'était.

## Preuve mesurée

Sur l'arbre sain, `LIVE` enregistre **16** checks. En le vidant, puis en
l'exécutant :

| | avant | après |
|---|---|---|
| verdict | `38 checks: 38 ok, 0 failed, 0 skipped` | idem — **inchangé** |
| ligne finale | `READY: every check passed.` | idem — **inchangé** |

Le sabotage passe inaperçu non pas malgré le gate, mais **grâce** à lui.

## Le correctif, deux gardes distinctes

Le défaut n'est pas « une liste peut être vide » — `LOCAL` vide serait un vrai
chiffre dans d'autres circumstances. Le défaut est qu'**une liste peut être vidée
sans que le gate le dise, et pendant que l'autre liste rapporte toujours vert**.

1. **Liste vide ⇒ `FAIL`, en nommant la famille.** `LOCAL` ou `LIVE` à zéro et le
   gate s'arrête en disant laquelle, parce qu'une famille entière de mesures
   vient de cesser d'exister et que la ligne rouge doit se lire sans deviner.
2. **Plancher `MIN_LIVE_CHECKS = 8`.** `LIVE` à moitié vide passe encore le test
   d'emptiness, et c'est **normal** : 38 checks dans `LOCAL` seul sont un vrai
   chiffre. Mais une `LIVE` rétrécie est un **produit qui a cessé d'être
   surveillé**. Le plancher est calibré sur la mesure : 8 est la plus grande
   moitié qui garde chaque famille représentée — relais (health, single, auth),
   packaging (update, asset, tarball, xml), moteur (lightpanda, cdp), session
   (roundtrip, pin, audit), surface (diagnostics, sockets, popup).

Mesuré : sabotage `LIVE` 16 → 7.

```
FAIL every registered check is decorated and resolvable
      LIVE registers only 7 check(s) (floor MIN_LIVE_CHECKS=8); the live half of
      the suite is the part that measures the running relay, the pinned extension
      and the installed popup, and a shrunken LIVE hides a shrunken product
```

Si vous retirez un check live, changez ce nombre **dans le même commit** et dites
dans les notes ce qui a cessé d'être mesuré. Une édition silencieuse du plancher
est exactement le bug que cette constante existe pour rendre visible.

## Le même défaut, un cran plus bas : `pristine`

En cherchant le premier, un second est apparu, de la même famille et avec la même
cause : **un dénominateur auto-référentiel**.

`pristine_copies_match_the_committed_product` comparait les copies stockées aux
fichiers du dépôt, et denominator = `len(list(pr_dir.iterdir()))` — les fichiers
**présents**. Supprimer une copie imprimait `8/8`. Vider le répertoire imprimait
`SKIP`. Les deux sont verts, et les deux sont des mensonges : un dénominateur
qui se compte lui-même ne peut pas détecter son propre rétrécissement.

Le plancher est ici **9**, mesuré sur les 9 baselines réellement livrées
(`artifacts_pristine/` est gitignoré et peuplé à l'exécution, donc une valeur
`expected` codée en dur pourrirait par design).

Et surtout **l'ordre** est le correctif à lui seul. Le plancher s'exécute :

```
garde du répertoire → PLANCHER → resolve() → git → boucle
```

**avant** `resolve()`, **avant** la lecture git, **avant** tous les `SKIP`. Une
base élaguée atteignait la branche git avec plus rien à résoudre et sortait par
`if not allowed: return "SKIP"` — sans jamais dire que les baselines avaient
disparu. Le message de `SKIP` est supprimé : un `SKIP` silencieux est une
mesure absente.

## Les deux planchers, pas un

Le correctif ci-dessus ne tient que pour `LIVE`. Mesuré le même jour : la même
attaque sur `LOCAL` passait aussi. `LOCAL` compte **38** checks, `LIVE` **16**.
Aucune des deux listes ne se vidait seule — on pouvait en retirer une seule entrée
et le verdict restait vert, parce que les invariants testés sont des tests
d'emptiness : une liste à 37 entrées n'en est pas une.

D'où deux constantes :

| constante | valeur | ce qu'elle interdit |
|---|---|---|
| `MIN_LOCAL_CHECKS` | 38 | un check local supprimé ou renommé hors de la liste |
| `MIN_LIVE_CHECKS` | 8 | une `LIVE` rétrécie sous la moitié qui garde chaque famille |

Refus réel, mesuré :

```
FAIL  LOCAL registers only 37 check(s) (floor MIN_LOCAL_CHECKS=38); a local check
      was deleted or renamed out of the list.
```

**Ordre mesuré, pas supposé.** Les planchers sont évalués **avant** la garde
« défini mais jamais enregistré ». Un sabotage qui retire `versions_agree` de
`LOCAL` est donc refusé par `MIN_LOCAL_CHECKS`, pas par la garde du
désenregistrement — le harnais A le montre : les deux refus sont vrais en même
temps, le premier lu gagne.

## Direction que `unwired` ne pouvait pas voir

`the_gate_cannot_contain_a_check_that_cannot_be_seen` gérait deux directions :
un nom enregistré sans fonction (`ghosts`) et un check enregistré sans `@check`
(`naked`). Une troisième n'existait pas : une fonction **définie, décorée, et
jamais enregistrée**. Elle ne casse rien — la boucle ne l'appelle pas — mais
rien ne le disait. Elle porte le `@check`, donc elle a l'air câblée, et elle
n'influence jamais le verdict.

Mesuré : ajout de `@check("...") def z_unregistered_sabotage()` sans l'ajouter à
`LOCAL` ni à `LIVE`.

```
FAIL  1 @check function(s) are defined but never REGISTERED in LOCAL or LIVE:
      z_unregistered_sabotage - they carry the decorator that makes a check look
      wired while nothing ever runs them
```

## Discrimination mesurée

| cas | avant | après |
|---|---|---|
| arbre sain | `ok 9/9` | `ok 9/9 stored baselines hold a version this repo actually committed` |
| `LIVE = []` | **`READY`** | `NOT READY`, nomme `LIVE` |
| `LIVE` 16 → 7 | **`READY`** | `NOT READY`, nomme `7` et le plancher `8` |
| répertoire `pristine` vide | **`SKIP`** | `NOT READY`, exige 9 |
| `pristine` 8 sur 9 | **`ok 8/8`** | `NOT READY`, exige 9 |
| copie non résoluble | `ok` partiel | `NOT READY`, nomme le fichier |

Chaque ligne de ce tableau est adossée à `scripts/proof_red_gate_wiring.py`,
qui rejoue la **vraie** fonction du gate sur une copie de son propre texte — pas
une assertion, pas une réimplémentation. Sortie mesurée :

```
6 named red, 0 unnamed, 0 invalid
control 1/1 ok
WIRING PROOF PROVEN
```

| cas | sabotage | refusé par |
|---|---|---|
| A | `LOCAL` 38 → 37 | `MIN_LOCAL_CHECKS = 38` |
| B | `@check` ajouté, non enregistré | « defined but never REGISTERED » |
| C | `LIVE` 16 → 7 | `MIN_LIVE_CHECKS = 8` |
| D | `artifacts_pristine/` supprimé | « 9 stored baseline(s) are required » |
| E | `pristine` 9 → 8 | « only 8 stored baseline(s) present, 9 required » |
| F | `LIVE = []` puis `LOCAL = []` | « LIVE/LOCAL is empty, so none of its checks ran » |

Un rouge **nommé** est un refus dont le message contient le mot attendu. Un refus
pour une autre raison compte `unnamed` et n'est pas une preuve — c'est ce qui a
fait échouer la première version du cas C : retirer **une** entrée de `LIVE`
(16 → 15) ne franchit pas le plancher, ce qui refuse est la garde du
désenregistrement, pas le plancher. Le cas n'a été validé qu'en descendant sous
`MIN_LIVE_CHECKS`, soit 16 → 7.

Les deux controls passent : l'arbre intact reste `ok` — 54 checks, 19 helpers, et
`9/9 stored baselines hold a version this repo actually committed`. Sans eux,
une garde patchée en « toujours `FAIL` » ferait passer ce fichier.

**Une ligne du tableau ci-dessus n'est pas couverte par le harnais** : « copie
non résoluble ». Cette direction exige que `resolve()` puis la lecture git
s'exécutent, or un temp tree n'a pas de dépôt — la check y répond `SKIP` avant
d'y arriver. Elle a été mesurée en exécutant la vraie fonction sur le vrai dépôt,
et elle le reste : c'est une mesure par exécution, pas une preuve rejouable par
`proof_red_gate_wiring.py`. Elle est écrite ici comme telle plutôt que comptée
parmi les six cas.

## Un check qui disparaissait au lieu de répondre

`the extension in Comet serves the repo version` était le seul check qui n'avait
aucune garde pour un prérequis externe. Mesuré 2026-10-04 : Comet était fermé,
`urlopen` a levé `URLError`, et l'exception a quitté le check **sans aucun
verdict**. Le gate a donc affiché

```
54 checks: 53 ok, 1 failed, 0 skipped
```

où le seul échec était précisément « on n'a pas mesuré ». Le compte est
juste, le message mentait sur sa propre nature.

Il répond maintenant `SKIP`, en nommant l'endpoint joignable :

```
SKIP  no browser on http://127.0.0.1:9223 to measure the loaded extension
      (URLError) - start Comet and re-run to measure it; an unreachable browser
      is an unmeasured check, not a passing one
```

Un navigateur fermé est une **mesure absente**, pas une mesure réussie. Le
compteur du gate tient la différence : `SKIP` n'est jamais compté dans `ok`.

## Deux runtimes qui se marchent dessus

Trouvé en exécutant cette release, pas en la relisant. Les 18 harnais
proof-red **éditent les fichiers du produit sur le disque** — `popup.js`,
`relay/server.py` — et aucun ne réserve son fichier : pas de `flock`, pas de
`msvcrt.locking`, pas de fichier de verrou.

J'ai donc lancé deux gate à la suite sans attendre la fin du premier (le
premier avait disparu du shell sans que je le confirme). Les deux exécutaient
des harnais qui sabotent les mêmes fichiers **en même temps**. Résultat
mesuré, trois échecs :

```
FAIL an unread branch is reported, never read as 'up to date'
      proof-red harness printed no tally: ['    FAILED (failures=3)']
FAIL every proof-red harness is REGISTERED and every sabotage is NAMED
      1 of 18 harness(es) did not prove cleanly: proof_red_session_expiry.py
      printed no tally
FAIL no stored 'pristine' copy can become a false reference
      1 stored cop(y|ies) hold bytes NO commit ever held: relay__server.py
      holds bytes no commit ever held for relay/server.py
```

Le troisième est le plus instructif : `relay/server.py`,
`scripts/artifacts_pristine/relay__server.py` et `HEAD:relay/server.py` ont le
**même sha256** maintenant. Le fichier n'est pas corrompu — un harnais avait
simplement refreshé la base pendant que l'autre sabotait, et ce check a fait son
travail en voyant des octets qu'aucun commit n'a eus. Rejoué en un seul run,
il répond `ok 9/9`.

Ce n'est pas corrigé ici : c'est une autre famille que les listes et la base,
et elle mérite son propre correctif. Mais l'écrire ici plutôt que de taire les
trois échecs : **un gate ne se lance pas deux fois**, et un rouge sur
`pristine` ou sur un tally manquant doit d'abord faire suspecter un run
concurrent avant d'être lu comme une régression.

## Ce que ce correctif ne fait pas

Le gate a toujours une fail silencieuse possible : `scripts/cdp_utils.py` lève
`SystemExit` **à l'import**, et `SystemExit ⊂ BaseException`, donc
`except Exception` dans le décorateur `@check` ne l'attrape pas. Le processus
meurt, **sans résumé de checks**. C'est observé en direct pendant la préparation
de cette release (le gate lancé avec l'interpréteur système s'est arrêté après
7 checks imprimés, `EXIT=1`, aucun verdict) — et c'est le défaut que la prochaine
release traite. Il n'est **pas** corrigé ici, et il est écrit ici pour que
personne ne croie que ce green-là est un green complet.
