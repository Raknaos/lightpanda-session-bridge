# 0.7.36 - a base that repairs itself toward the damage

## The defect

The proof-red harnesses keep byte copies of product files under
`scripts/artifacts_pristine/`. When a copy differs from the file on disk, the
harness REFRESHES it from that file. That is the right defence against a stale
copy, and it is the hole.

A killed run can leave the PRODUCT sabotaged. The next run notices the copy is
out of date and refreshes it from the sabotage. From then on that copy is the
false reference: every restore-verification compares against damaged bytes and
passes. The 0.7.35 fence cannot see it either - that fence hashes the product,
and the pristine is not the product.

Measured, both directions:

- pristine poisoned + healthy product heals CORRECTLY (it refreshes to the
  product)
- healthy pristine + sabotaged product heals to the SABOTAGE, and the pristine
  then equals the sabotage

## The invariant

Not "the copy equals HEAD". I tried that first and it failed on a perfectly
healthy tree: five copies held an older build, each byte-identical to a real
commit (8e22d1ea, 4892f9f3, 2b7d2a52). A harness that ran before a release
wrote them. An old copy is harmless - the next run refreshes it. Requiring HEAD
made the check fail for no reason, which is worse than having no check.

The invariant that survives: **a copy must hold a version of its source that was
actually committed**. Bytes no commit ever held can only have come from a
sabotage, and that is exactly what a self-healing harness installs as its base.

```
FAIL no stored 'pristine' copy can become a false reference
  1 stored cop(y|ies) hold bytes NO commit ever held:
  relay__updater.py holds bytes no commit ever held for relay/updater.py
  - a harness refreshes these from the file on disk, so a killed run can
  install the damage as the base it verifies against
```

## The list, discovered

The first version of this check hard-coded five (name, product) pairs and
answered `5 pristine copies all equal the committed product`. There were 18
copies on disk. Thirteen were never examined, and the confident count of a
partial set read as a whole - a guard that enumerates a subset publishes a
number nobody can trust.

Worse, the five pairs were written from my own reading of a couple of harnais.
`relay.replace("/", "__")` builds its copy name at runtime, so no literal search
finds `relay__server.py`, `relay__updater.py` or `extension__popup.js`. The
conventions are now read out of the harnesses themselves:

- `artifacts_pristine / "<name>.pristine"` - `popup.js.pristine` (4 harnesses),
  `diagnostics.py.pristine`
- `artifacts_pristine / "<name>"` - `popup.js`, `updater.py`
- `PRISTINE / rel.replace("/", "__")` - built, no literal in the source
- `popup.js.proof_red_<harness>` - rollback, update_failure

A name matching none of them is reported by name, never skipped. The check now
reports `11/11 copies hold a version this repo actually committed`.

## Order matters

This check runs BEFORE the harnesses. A self-healing harness repairs the very
evidence the check reads: placed after, it measured 5/5 correct while the copy
was poisoned, and stayed green under a real sabotage I could reproduce.

## My own sabotage was dead

The first attempt to prove it poisoned `popup.js` by replacing `0.7.35`.
`popup.js` contains no such string, so the replace changed nothing and the gate
reported green. A `str.replace` whose pattern is absent is a silent no-op - the
same defect class as a check whose pattern no longer matches. The pattern is
now read out of the file and the test asserts the bytes actually changed before
it trusts the result.
