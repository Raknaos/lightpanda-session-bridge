## Fixed
- **x.com could never sync — a permanent "5/7 localStorage keys".**
  x.com keeps two of its entries under 194-character names
  (`rweb.sessionBinding.hashClaim:<base64>`). The snapshot filter dropped every
  key name longer than 128 characters **silently**, so those two were removed
  before the first write attempt: Lightpanda received 5 of 7 keys, the popup
  honestly reported the ratio, and syncing again could never fix it — the
  missing keys never even left the relay.
- Key names up to **1024 characters** and values up to **256 KiB** are now
  carried, with the whole snapshot bounded at **1.5 MB** so it still fits the
  import body cap.
- **Nothing is dropped in silence any more.** A key the relay cannot carry
  (name or value past the bounds, or a snapshot past the total) is reported
  **by name**, with its size and the reason, on both the HTTP and the CLI path —
  instead of turning into a ratio that can never reach 100%. The
  incomplete-transfer message now names the missing keys too.

## Added
- `storage_expected`, `storage_missing` and `storage_refused` in the import
  response (success *and* failure), so the popup builds a translated, specific
  message instead of showing the relay's raw text. New i18n strings in all 10
  languages.

## Proven on x.com, end to end
The live tab's session was read from the browser, imported through the real
`POST /v1/session/import`, then verified **inside** Lightpanda:

- 7/7 localStorage keys present, including both 194-character names, zero extras
- `x.com/home` loaded as the logged-in account (profile link, account switcher
  and composer all present)
- the session survived two further navigations (`/home`, `/notifications`),
  still 7/7 and still authenticated

Key names and sizes only — no cookie or localStorage **value** was ever printed,
logged or written to disk.
