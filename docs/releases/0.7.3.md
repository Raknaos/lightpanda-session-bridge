# v0.7.3 - the restored session can no longer be injected twice

## The defect

`_restore_persisted_session()` runs on the HTTP server's threads and is called
from two places - `proxy_cdp()` (agent traffic) and the session-import handler.
Its old shape:

```python
if _PERSISTED_APPLIED or not _LAST_SESSION:
    return False                      # <- read
try:
    with CDP_LOCK:
        _apply_session(...)           # <- CDP call, can block for seconds
    _PERSISTED_APPLIED = True         # <- write, outside every lock
    return True
except Exception:
    return False
```

Read and write are separated by the CDP call with no lock held, so both threads
pass the check. `_apply_session` calls `Network.setCookie`, which SETS a cookie
rather than replacing a set - so the same jar gets every cookie twice. The window
is small but permanent: it is the normal startup race, exactly when a relay has
just been restarted and the first agent request arrives.

Two more things were wrong with the same block:

- `except Exception` cannot tell "Lightpanda is down, try again" from "this is
  structurally broken". Both return `False`, so the relay went on listing a
  session it had never injected - a healthy-looking relay with an empty jar.
- `CDP_LOCK` was the wrong lock even for the CDP call. It protects the socket.
  It says nothing about whether the "already restored?" question has been
  answered.

## The fix

A `STATE_LOCK` claim (`_PERSISTED_INFLIGHT`) taken under the lock before the CDP
call, and resolved in a `finally`-shaped release after it. The session is
snapshotted (copied) before use so a caller cannot mutate the relay's own copy
mid-apply. The blanket `except` is gone: transient failures raise the retryable
types the callers already handle, and the claim is released either way so a
later call retries.

## Verified

Both sabotages go red, not just the happy path:

- claim removed -> `_apply_session ran 2 times for ONE restored session
  (callers: ['Thread-1 (run)', 'Thread-2 (run)'])`
- old `except` restored -> `AssertionError: ValueError not raised`

A first attempt at the proof was hollow: the sabotage command was
`python -m unittest tests.test_restore_race`, which failed with
`ModuleNotFoundError` (`tests/` is not a package) - a red run that proved
nothing. Running the file directly exposed that the sabotage had not been
applied to the right place at all.

169 tests green, gate 28/28, and verified after a real relay restart: import 200,
`attached: true`, `cdp_attached: true`, no cookie values in the report.
