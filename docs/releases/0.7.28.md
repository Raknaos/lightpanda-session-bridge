# 0.7.28 — chaque état possède le libellé du bouton

## Le défaut, mesuré sur le vrai `renderUpdateCard`

Sorti directement de la règle que 0.7.27 vient d'établir — un libellé est une
propriété d'un **état**. `updateBtn.textContent` n'était écrit que dans la
branche `update_available`.

Les trois autres sorties — relais muet, GitHub en erreur, rien à installer —
laissaient donc le bouton portant la version qu'un rendu précédent proposait.

| Rendu | Libellé attendu | Avant |
|---|---|---|
| mise à jour en attente (release) | `Mettre à jour vers v0.7.28` | idem |
| **puis mise à jour de branche** | `Installer le dernier commit` | **héritait de la release** |
| **puis relais muet** | aucun | **`Installer v0.7.28`** |
| **puis installation en cours** | aucun | **`Installer v0.7.28`** |

Le cas réellement visible n'est pas « relais muet » — le bouton y est masqué.
C'est **release puis branche** : une mise à jour de branche a son propre
libellé, qui ne nomme **aucune version**, et il héritait de celui d'une release.
Le bouton affichait donc « Installer v0.7.28 » pour une mise à jour de commit.
C'est le nœud sur lequel l'utilisateur clique.

## Le correctif, même règle que 0.7.27

```js
updateBtn.textContent = '';
```

semé à côté de `updateMeta.title = ''`. Une fois qu'un correctif ajoute une
graine, c'est une affirmation que la classe est fermée — donc le passage
immédiat est de compter, pour chaque fonction de rendu, combien de sorties
écrivent chaque propriété. Toute propriété dont le compte est **inférieur au
nombre de sorties** est le même défaut.

Passé sur les quatre autres fonctions de rendu — `renderSessions`,
`checkRelay`, `applyTranslations`, `copyDiagnostic` : **propres**.

## Deux fautes de harnais, dont une invisible dans les diff

- Mon `expect` disait « a dead relay **does not keep** the version » alors que
  le runner imprime « a dead relay **keeps** the version ». Le rouge était
  correct, la preuve refusée. C'est la troisième fois que le nom recopié
  diffère du nom réel : lire la ligne imprimée, jamais la reformuler.
- Mon stub de `t()` concaténait inconditionnellement, alors que le vrai contrat
  appelle une **fonction** ou formate un `{0}`. Il rendait `updateBtn\0v0.7.28`,
  **avec un caractère NUL réellement écrit dans le fichier** et invisible dans
  toutes les diffs lues ensuite. Corrigé en lisant la définition de la clé dans
  le dictionnaire, puis en comptant les octets de contrôle sur tous les fichiers
  touchés — 0 sur les six.

Un harnais peut donc épingler un défaut que le produit n'a pas : c'est le mode
d'échec du point 65, arrivé par le stub plutôt que par un littéral écrit à la
main.
