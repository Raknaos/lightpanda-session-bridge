# 0.7.33 - the sabotage proofs nobody was required to run

## The defect

`scripts/` holds seventeen proof-red harnesses. Before this release the gate named
twelve. Five were never executed by any commit:

| harness | sabotages | what it proves |
|---|---|---|
| `proof_red_update_channel.py` | 11 | the update channel's comparison logic |
| `proof_red_session_expiry.py` | 8 | the popup's expiry rendering |
| `proof_red_route_deadline.py` | 4 | the relay's route timeout |
| `proof_red_popup_deadline.py` | 2 | the popup's AbortController deadline |
| `proof_red_socket_timeout.py` | 1 | a silent connection is released |

Twenty-seven sabotage proofs had never been required to be red. The gate read
`READY` on every commit that touched the code they sabotage.

Three of the seventeen printed **no tally at all** - `popup_deadline`,
`route_deadline` and `socket_timeout` ended on a bare `PROOF RED: yes`. Even a
correctly wired check could not have told `4/4 named red` from `4 reds of which
2 are unnamed`, because the number it needs was never printed.

## The fix

One check, `every proof-red harness is REGISTERED and every sabotage is NAMED`,
discovers every `scripts/proof_red_*.py` by glob and runs it. Discovery, not a
list of names: a literal name is one line to forget, which is exactly how these
five went unwired. A new harness is required the moment it exists.

The tally is parsed in one place, `proof_red_tally`, which reads all four
spellings the harnesses already print and returns `None` when it recognises
none. The three silent harnesses now print the named / unnamed / invalid
counters themselves, counting from the variables they already had.

`socket_timeout` also gained an import-failure refusal: a suite that cannot be
imported is a harness failure, never evidence.

## What the check could have missed

Two of my own steps were wrong, and both were found by measuring rather than by
reasoning.

**The registration guard was decorative.** It searched the whole `acceptance.py`
for the check's name - and a defined check's name appears in its own `def`, so
removing it from `LOCAL` left it "registered" and the audit stayed green under
the exact sabotage it exists to catch. This is point 13 of the release gate with
a different payload. The audit now reads the `LOCAL`/`LIVE` list blocks.

Proof in one table, both directions:

| direction | exit | expected |
|---|---|---|
| intact | 0 | green |
| removed from `LOCAL` | 1 | red |
| registered, decorator deleted | 1 | red |
| glob removed | 1 | red |

The file was restored byte-exact from a pristine snapshot taken at sabotage time.

**The gate must be able to go red.** Muting one harness's tally so the parser
could not read it produced `NOT READY`, exit 2, with two named failures:

```
FAIL every proof-red harness is REGISTERED and every sabotage is NAMED
     1 of 17 harness(es) did not prove cleanly:
     proof_red_scrubber.py printed no tally - the check cannot tell a named red
     from an unnamed one
```

## A timeout is not a restore

While proving the gate's influence, an `execute_code` cell was killed at 300 s
holding a live edit to `relay/diagnostics.py`: `scrub()` replaced by `_short()`
on `update_note`, which would have shipped a truncated token into a report meant
to be pasted in public. The killed cell never ran its `finally`. Both the
harness and the product file were restored from pristine snapshots taken before
the sabotage, and `git diff` confirmed `relay/diagnostics.py` is identical to
HEAD again.

The lesson is point 31 with a new ending: a timeout does not merely lose kernel
state, it leaves the PRODUCT modified. Check `git status` after any interrupted
proof run, and restore by bytes from a snapshot, never with `git checkout`.
