# v0.7.16 — a popup that painted one wrong-language frame before any script ran

## The defect

`#diag-text` shipped a French literal:

```html
<button id="diag-btn" class="diag-btn" type="button">
  <span id="diag-text">Copier le diagnostic</span>
</button>
```

A literal in `popup.html` is **painted before `popup.js` can translate it**.
`applyTranslations()` does rewrite it — line 821, `diagText.textContent = t('diagBtn')` —
so the settled panel was always correct, in every one of the ten languages. But
every English install flashed French on every open, for the frame or two before
the script ran. The product was right and briefly lied about it.

The default language is `en`, which is what makes this a defect rather than a
harmless leftover: the panel the majority of installs see first is the one that
flashes the wrong language. Five sibling elements (`#relay-text`,
`#label-update`, `#btn-text`, `#footer-secure-tag`, `#update-chip`) already
shipped English literals — `#diag-text` was the odd one out, left over from when
the panel was French-only.

## Measured, not assumed

`scripts/measure_first_paint.py` loads the **real** `popup.html` in the **real**
Comet over CDP, twice:

- **pass 1** — `Emulation.setScriptExecutionDisabled: true`, which is exactly the
  frame the user sees before any script executes
- **pass 2** — scripts enabled, the settled state

Any element that differs between the two passes is a flash.

```
element                1er rendu (sans JS)                apres rendu (avec JS)
#diag-text             'Copier le diagnostic'             'Copy diagnostic'  <-- FLASH
#relay-text            'Checking…'                        'Checking…'
#label-update          'Bridge update'                    'Bridge update'
#btn-text              'Sync to Lightpanda'               'Sync to Lightpanda'
#footer-secure-tag     'Isolated Profile · Localhost CDP' 'Isolated Profile · Localhost CDP'
```

The five control-group elements are identical across both passes. That is what
makes the sixth meaningful: the flash was specific, not a harness reading noise.

The harness proves itself in both directions — sabotage `Copy diagnostic` →
`Copy diagnostic` moved the count from **1 flash to 0**, and the restore was
byte-identical (`cmp -s`).

## The gate bug this surfaced

Registering the check produced something worse than the flash:

```
17 checks: 16 ok, 0 failed, 0 skipped
READY: every check passed.
```

**Seventeen executed, sixteen counted** — while the popup was still flashing
French. `@check` is a decorator, not a convention: without it the function runs
but never calls `record()`, so it never reaches `RESULTS` and cannot influence
the verdict. A check can therefore be green-shaped, present in `LIVE`, and
completely inert. The only reason this was caught is that the header line
(`acceptance: 17 checks`) disagrees with the summary line, and the two numbers
were printed by the same run.

This is the sharpest form of the decorative check recorded so far: not a check
that cannot fail, but a check that **cannot be seen to have run**.

## Verification

| | Measured |
|---|---|
| First-paint measurement, before fix | 1 flash, `#diag-text` |
| First-paint measurement, after fix | **0 flash** |
| Sabotage proof (both directions) | 1 → 0, restore byte-identical |
| Gate check under sabotage | `FAIL … 'Copier le diagnostic' … <-- FLASH` |
| Gate, restored | **18 local + 17 live READY** |
| First paint after release | `Copy diagnostic` in `en` |

## Note on process

The commit for this version went in while the gate was red — `versions agree
everywhere` had failed because `docs/releases/0.7.16.md` did not exist yet. The
release-acceptance rule is not "write the note first", it is **no commit until
the gate is green**, and a red gate is not something to be noted and stepped
over. Recorded here because the failure mode is the interesting part: the same
run that produced the release also contained the gate's own verdict, and the
commit proceeded anyway.
