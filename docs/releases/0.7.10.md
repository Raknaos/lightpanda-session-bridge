# v0.7.10 - the diagnostic report exported the tab URL, token and all

## What was happening

`copyDiagnostic` documents its own guarantee on the line above the code:

```
// the relay's sanitized report (versions, counts, live state - no cookie, no
// token, no URL) and puts it on the clipboard so a bug report carries evidence.
```

and three lines below it did this:

```js
'tab: ' + (currentTab ? currentTab.url : 'unknown'),
```

`currentTab.url` is the full URL. It routinely carries `?token=`,
`?access_token=`, `#access_token=` or a session id in the query or the fragment.
So the one artifact whose entire purpose is to be pasted into a public issue
exported the credential of the page you happened to be on - while claiming it
does not. The rest of the popup already narrows to `new URL(url).origin` for
syncing; only the report copied the whole thing.

The fix is a `reportableOrigin` helper and one line of report:

```js
'site: ' + reportableOrigin(currentTab ? currentTab.url : ''),
```

## The test, and why the first one was decoration

The first version of the test rebuilt the report array itself instead of reading
it from the file. It passed with the leaking line put back - the sabotaged
`popup.js` restored `currentTab.url` and the suite still reported *OK*. A test
that retypes production code is a second program that can drift without anyone
noticing.

The test now extracts the real `const report = [...]` literal out of `popup.js`,
drops it into a sandbox with a real `URL`, and runs it over eight URL shapes -
plain, token in query, token in fragment, session id, userinfo plus path,
non-http page, empty, absent. Under the old code:

```
FAIL  token en query       *** VALEUR FUITE ***  query/fragment present
FAIL  token en fragment    *** VALEUR FUITE ***  query/fragment present
FAIL  session id           *** VALEUR FUITE ***  query/fragment present
FAIL  userinfo + chemin    origin absent -> "relay ok\n\n--- extension side ---\n
                                     popup: v0.0.0\ntab: https://u:p@host.tld/a/b?q=1#frag\n
                                     language: fr"
```

The failure prints the whole report, so the proof shows the secret leaving rather
than a count.

This is now the 29th gate check, registered in `LOCAL` - a check nobody runs is
not a check.

## The audit finding that was wrong

The delegated audit reported the bootstrap endpoint as CRITICAL: *"hands the
bearer token to anyone who sets one forged header... Proved live: curl -H
"Origin: chrome-extension://..." -> 200"*.

Re-tested against an isolated relay on port 8899 with a throwaway config dir:

```
aucun Origin (curl/probe local)              403
chrome-extension:// FAIT-MAISSON (officiel)   200 {"ok": true, "token": "<43 chars>"}
chrome-extension:// invente (32 car)          403
http:// (page web)                           403
pinned_extension_id existe : False
```

The forged id is refused and no pin is written. The reason is that
`_load_pinned_extension_id` falls back to `OFFICIAL_EXTENSION_ID` when no pin
file exists, which makes `auto_pin=True` unreachable in practice. The audit's own
probe had pinned the forged id before measuring - it was describing the poisoning
scenario (which is real: a pin file naming a stranger makes that stranger the
trusted caller) while reporting it as the default.

Reporting a finding and reproducing it are different skills. The accusation was
specific and cited line numbers, and it was still wrong in a way that would have
added a fix to a correct security check.
