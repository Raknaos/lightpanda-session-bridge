# 0.7.21 — le rapport de diagnostic dit *pourquoi*

## Le trou

Le rapport de diagnostic est ce que l'utilisateur colle dans un bug. Il portait
`update_available = False` et rien d'autre.

C'est vrai et inutile : impossible d'y distinguer « rien de nouveau » de « une
mise à jour qui traîne ». La page censée décider laquelle des deux est ne
donne aucune raison. Le popup, lui, disait déjà pourquoi depuis 0.7.20.

Le rapport publie désormais l'état **mesuré** et la raison :

```
update_available = False
update_state = unknown
update_note = deployed commit ef1d6420 is the latest that touched extension/
update_version = 0.7.20
update_commit = 3343def9...
update_latest = ef1d6420...
```

`update_state` ∈ {`same`, `differs`, `unknown`} — et `unknown` signifie
« pas mesuré », jamais « pas de mise à jour ».

## La fuite que cet ajout a introduite

`update_note` est écrit par le **relais**. C'est du texte étranger. Il vivait
dans un dict que `diagnostics.py` construit — donc jamais scrubbé, parce qu'une
donnée construite ici est trusted by construction.

Une note lisant `Authorization: Bearer ghp_A1...Q7r8` exportait **12 caractères
d'un jeton** dans un rapport dont le seul but est d'être collé publiquement.

Trouvé par le harnais de preuve, pas par la relecture : le test de
confidentialité plantait avec `'ghp_A1' unexpectedly found in ...`.

Le correctif est `scrub(data.get("note") or "") or None`. Le scrubber sait déjà
distinguer l'entropie d'un métadonnée, donc :

- note avec un jeton → `[redacted]`
- note avec un sha → **intacte**, `main moved to cb4bdf5, but the deployed tree
  is byte-identical`

Le cas inverse est figé par un test, parce qu'un scrubber trop large est un
défaut de même gravité qu'une fuite (point 16 du skill).

## Un check du gate était vert sans mesurer

Trois checks lisaient la sortie des suites Node avec
`l.strip().endswith("passed")`. Les suites impriment `18 passed, 0 failed` —
une ligne qui **finit par « failed »**. Le motif ne matchait rien, la valeur
par défaut `?` était renvoyée, et le verdict affichait :

```
ok   the update card says WHY nothing is offered  ?
```

Vert, et aveugle. Même famille que le point 13 du skill, un cran plus bas : là
le check ne s'exécutait pas, ici il s'exécutait entièrement et sa mesure était
jetée à la poubelle.

La mesure est maintenant cherchée **partout dans la ligne**
(`re.search(r"\d+\s+passed")`), et une mesure absente est un **FAIL** — jamais
une valeur par défaut silencieuse.

Prouvé influent : le harnais Node rendu muet fait passer le gate de `READY` à
`NOT READY` avec le message exact.

## Le CHANGELOG était un fichier collé sur lui-même

En cherchant où insérer cette entrée, j'ai trouvé que `CHANGELOG.md`
portait **74 entrées pour 37 versions** — l'historique entier collé deux fois,
34 entrées identiques au caractère près — et que l'entrée `0.7.20` était
**soudée sans saut de ligne** au milieu d'une puce de 0.3.3 :

```
- Loopback-only socket binding (`127.0.0.1`).## [0.7.20] - le popup dit POURQUOI...
```

avec un paragraphe répété deux fois dans la même entrée.

Aucun check ne le voyait : `versions_agree` demande si `## [<version>>` apparaît.
Il apparaît — dans les deux moitiés. Un test de présence ne peut pas voir une
duplication.

Réparé : dédupliqué (40 entrées, 40 titres distincts), collage coupé, ordre
antéchronologique rétabli, addendum rangé après sa version.

Et surtout, un check qui empeche la recurrence — `changelog_is_not_duplicated`, qui
mesure trois invariants qu'aucun test de présence ne peut voir :

1. aucun titre d'entrée en doublon ;
2. les versions sont en ordre décroissant ;
3. aucun titre soudé à de la prose.

Prouvé influent sur les trois formes (historique collé, entrée soudée, ordre
inversé), vert sur le fichier réparé.
