# 0.7.24 — « GitHub m'a refusé » n'est pas « le relais est mort »

## Le défaut, mesuré sur le relais vivant

`/health` répondait **200, `ok: true`** — et la carte de mise à jour affichait
**« Relais hors-ligne »**.

Les deux situations arrivent par le même prédicat `!updateInfo.ok` :

| État | Ce que c'est | Ce que l'utilisateur doit faire |
|---|---|---|
| `updateInfo === null` | le relais n'a pas répondu | démarrer son relais |
| `updateInfo.ok === false` + `error` | le relais a **répondu**, GitHub a refusé | attendre, ou poser un jeton |

Le popup renvoyait « relais hors-ligne » dans les deux cas : on envoyait
l'utilisateur déboguer une installation parfaitement fonctionnelle.

Et le relais publiait `error_kind` (`rate_limit` / `unreachable`) depuis le
début — **`error_kind` n'apparaissait pas une seule fois dans `popup.js`**.
L'information existait, elle n'était simplement pas lue.

## Le correctif

La carte distingue la panne locale de l'échec amont :

- `error_kind === 'rate_limit'` → « Limite GitHub atteinte · réessaie plus
  tard »
- autre erreur amont → « GitHub n'a pas répondu »
- `ok: false` **sans** `error` → reste « Relais hors-ligne » (le cas genuinely
  indistinguable)

Le message brut du relais — qui nomme la limite et l'identité de l'appelant —
va dans **l'infobulle**, jamais dans le panneau : c'est une ligne de journal, pas
de l'UI, dans un popup à dix langues.

Deux clés i18n nouvelles dans les **10 langues**.

## Preuve

`test_update_card_truth.js` : 51 -> **67** tests. Chaque phrase est comparée
par **égalité exacte** à la chaîne du dictionnaire, et le sens inverse est
asserté : `ok: false` sans `error` reste « hors-ligne », et une erreur amont
**autre** qu'un rate limit ne prétend pas « limite atteinte ».

`scripts/proof_red_upstream_card.py` : **4 sabotages, 4 rouges nommés, 0
invalide**, `popup.js` restauré à l'octet.

| Sabotage | Rouge nommé |
|---|---|
| A — re-fusionner les deux échecs en `relayOffline` | `chip="Relais hors-ligne"` |
| B — lire `error_kind` puis l'ignorer | `"GitHub n'a pas répondu" != "Limite GitHub atteinte…"` |
| C — revendiquer une limite pour **toute** erreur amont | `meta="Limite GitHub atteinte…"` |
| D — mettre le message brut dans le panneau | `meta="API rate limit exceeded for 203.0.113.9"` |

Check `an upstream GitHub failure is not reported as 'Relay Offline'`
enregistré dans `LOCAL`.

## Une preuve d'influence qui ne prouvait rien

Première tentative : j'ai retiré du harnais la garde « sabotage mort » — le
gate a affiché `4/4 named red` et `READY`. **C'était correct** : les quatre
sabotages rougesaient tous réellement, donc la garde n'était jamais exercee. Une
garde peut être supprimée sans que la preuve ne le remarque ; seul le **compte**
porte.

L'influence se prouve en dégradant une attente pour qu'elle cesse de matcher :
`3/4 named red, 1 unnamed` + `NOT READY`, exit 1.

Deux `PATCH-MISS` ont preceded cette mesure — **les miens**, pas ceux du
produit : j'ai écrit l'ancre de mémoire (13 espaces) alors que le fichier en
avait 5. Lire la ligne avant de la citer, y compris dans son propre fichier
écrit quelques minutes plus tôt.

Gravé : points **71** (un champ publié que personne ne lit est un défaut du
**consommateur**) et **72** (prouver l'influence demande un sabotage qui change
le **compte**).
