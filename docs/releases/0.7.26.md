# 0.7.26 — l'annulation est de nouveau possible après une installation

## Le défaut, mesuré sur le vrai `renderUpdateCard`

`rollbackBtn.style.display` était calculé **correctement** en haut de la
fonction :

```js
rollbackBtn.style.display = (updateInfo.backup_available && !updateInfo.update_available) ? '' : 'none';
```

Cette condition est **exactement** l'état de la branche « rien à installer ».
Puis, 58 lignes plus bas, cette branche terminait par :

```js
updateBtn.style.display = 'none';
rollbackBtn.style.display = 'none';   // ecrasait le calcul correct
```

Le bouton d'annulation n'était donc joignable **que** lorsqu'une mise à jour
était **en attente** — et jamais dans le seul état où il sert : juste après en
avoir installé une.

| Situation | Avant | Après |
|---|---|---|
| rien à installer, **sauvegarde disponible** | caché | **joignable** |
| rien à installer, aucune sauvegarde | caché | caché |
| branche avancée, sauvegarde disponible | caché | **joignable** |
| mise à jour en attente, sauvegarde disponible | joignable | joignable |
| mise à jour en attente, aucune sauvegarde | caché | caché |

Le relais avait mesuré `backup_available: true`, le popup **avait lu** le champ
— puis la lecture avait été jetée un écran plus bas. Ce n'est pas un champ
ignoré comme `error_kind` en 0.7.24 : c'est une valeur lue puis annulée.

## Les deux sens sont assertés

Afficher « annuler » sans sauvegarde derrière serait aussi faux que le cacher
alors qu'il y en a une. Un correctif qui afficherait le bouton
inconditionnellement échoue donc aussi — et le test le vérifie sur cinq états
plus le relais muet.

## Preuves

- `tests/node/test_rollback_reachable.js` : **7 verts**, sur le vrai
  `renderUpdateCard` avec le vrai dictionnaire.
- `scripts/proof_red_rollback.py` : **1/1 rouge nommé** (2 assertions rouges,
  `5 passed, 2 failed`), `popup.js` restauré à l'octet.
- Nouveau check `LOCAL` `undo_is_reachable_after_install`, enregistré et **prouvé
  influent dans les deux sens** : check aveugle → `27 ok, READY` ; produit
  réellement saboté → `NOT READY`, exit 1, avec le message nommant la cause
  (`popup.js is red on disk`) au lieu d'un générique « no tally ».

## Un défaut de harnais dont le produit ne sufferait pas

`_node_pass_count()` itère son argument. Les quatre appelants existants lui
passent une **liste** de lignes ; mon nouveau check lui passait une **chaîne** —
la fonction itérait alors les caractères, renvoyait `None`, et le check échouait
en affichant « undo suite : 7 passed, 0 failed », c'est-à-dire la preuve même
que la suite était verte. Même famille que le point 58, un cran plus bas :
l'enfant était parfaitement sain, sa mesure avait été jetée.
