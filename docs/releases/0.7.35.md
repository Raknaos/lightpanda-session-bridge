# 0.7.35 - a fence that hashes the damage and calls it the reference

## The defect

v0.7.34 added the fence: fingerprint every file a proof-red harness edits,
before and after the family runs, refuse any difference. It was correct about
what it claimed to watch - a harness that fails to restore - and **blind to
everything else**.

It compared the tree to **its own starting state**. A tree that was *already*
dirty when the gate began hashed the damage and reported `byte-identical`:

```
ok  the product is byte-identical after every proof-red harness has run
    17 harness(es) ran, 4 product file(s) byte-identical before and after
```

That line was printed on a run whose `relay/diagnostics.py` carried a leftover
sabotage. The fence cannot see the sabotage left by a session that ended before
it - which is the exact case v0.7.34 was written for, one run too late.

**Two questions, not one.** Before-and-after answers "did this run change
anything?". Against-the-committed-tree answers "is this tree what I think it
is?". Only the second catches a tree that was already wrong.

## The fix

The fence now reads `git show HEAD:<file>` for each target and compares. The
detail that mattered: **an unreadable reference is a `SKIP` naming its reason,
never a silent match.** Returning `None` from a failed read and letting it match
would have produced the same green on a runner without git - point 58's shape,
one level down.

Proven, message and all:

```
FAIL the product is byte-identical after every proof-red harness has run
     1 product file(s) differ from the COMMITTED tree: relay/diagnostics.py
     - a sabotage survived an earlier run, and this one hashed the damage
     as its reference (restore from a snapshot, never git checkout)
```

## The order I got wrong twice

The first run of the fence fired on a genuine leftover and reported the **harness
verdict**, with the drift in a later branch. I reordered it. It fired again with
the same wrong branch, because the reorder had moved `bad` after `uncommitted`
but the harness verdict was still reachable first in the sequence I had actually
written. Reading the real branch order - not the one I remembered writing -
fixed it, and both directions now report the live defect:

| state | branch reached first |
|---|---|
| harness left a file modified | `drifted` |
| tree dirty before the run | `uncommitted` |
| a harness reported badly | `bad` |
| git cannot answer | `SKIP` |
| all clean | `ok` |
